Palantir Learn의 **파운드리 기초 과정**을 들었다. 데이터 플랫폼의 기본 개념부터 온톨로지와 애플리케이션, 기존 시스템과의 통합까지 짧은 영상으로 살펴보는 입문 과정이다.

## 내용 정리

### 1. 파운드리란?

**한 줄 정의: 파운드리는 운영 의사결정 플랫폼이다.**

백엔드 엔지니어와 데이터 분석가뿐 아니라 현장 작업자, 운영 담당자, 경영자까지 데이터를 바탕으로 실제 업무에 영향을 주는 결정을 내릴 수 있도록 지원한다. 국방·정보, 백신 배포, 제조 최적화 같은 미션 크리티컬한 문제를 비롯해 의료, 자동차, 소매, 광업, 보험, 유틸리티, 공급망 등 다양한 산업에서 쓰인다는 소개가 나온다. 민감한 재무 정보, 개인 식별 정보, 건강 정보와 정부 데이터 등을 다루는 만큼 보안과 규정 준수도 플랫폼의 중요한 전제다. 강의에서는 HIPAA, GDPR, ITAR 같은 규제 프레임워크를 예로 든다.

**왜 운영 의사결정 플랫폼이 필요한가?**

- 데이터와 분석 도구에 투자해도 데이터팀·분석팀·운영팀이 서로 다른 언어와 도구를 쓰면 조직 전체의 협업으로 이어지기 어렵다.
- 대시보드나 모델을 만들고 배포하는 데서 끝나면, 그 결과로 내린 결정이 다시 데이터와 모델에 반영되지 않을 수 있다.
- 강의에서는 이런 단절을 데이터가 수집·가공된 뒤 보고서나 모델 형태로 전달되고, 실제 결정과 피드백은 원래 시스템에 되돌아가지 않는 **‘데이터 조립 라인’**에 비유한다.
- 파운드리는 공통된 조직 표현을 두고 데이터·분석·운영을 연결해, 결정과 현장의 피드백이 다시 업무 시스템으로 이어지는 구조를 지향한다.

그 연결의 중심에 온톨로지와 온톨로지를 사용하는 애플리케이션이 있다. 첫 영상에서 기억할 내용은 **Foundry는 분석 결과를 보여주는 데 그치지 않고, 여러 역할의 사용자가 실제 운영에 활용하고 그 결과를 되돌려 주는 플랫폼**이라는 점이다.

### 2. 온톨로지란?

**핵심:** 온톨로지는 조직의 데이터·모델·업무 활동을 공통된 디지털 표현으로 연결하는 Foundry의 중심이다.

강의에서는 온톨로지를 세 층으로 설명한다.

1. **시맨틱 레이어(Semantic layer) — 조직의 명사와 관계**
   - 사람·장소·사물·이벤트처럼 조직에서 중요한 대상을 공유된 디지털 표현으로 만든다.
   - 예를 들면 매장, 고객, 거래, 물류센터, 제품이 객체가 되고, 이들 사이의 관계와 데이터·모델로 계산되는 동적 속성이 연결된다.
   - 각 팀이 같은 대상을 같은 의미로 이해할 수 있도록 하는 조직의 공통 언어다.
2. **키네틱 레이어(Kinetic layer) — 조직의 동사와 행동**
   - 고객이 거래를 완료하거나 제품을 물류센터에서 매장으로 보내는 것처럼, 객체와 이벤트에 대해 수행하는 행동·기능·업무 과정을 표현한다.
   - 데이터를 읽는 것뿐 아니라 온톨로지의 대상을 실제로 움직이게 하는 층이다.
3. **동적 레이어(Dynamic layer) — 시뮬레이션과 최적화**
   - 여러 시나리오를 탐색하고, 선택이 후속 운영에 어떤 영향을 주는지 확인한다.
   - 가정과 결정 결과를 운영에 연결해 전략과 실행 사이의 피드백을 이어간다.

**온톨로지를 채우고 활용하는 흐름**

- 파이프라인으로 테이블, 센서, 거래 시스템, 지리공간, 타사 데이터 등을 연결한다.
- 연결된 데이터를 고객·제품·가격·창고처럼 업무에서 이해할 수 있는 객체로 모델링한다.
- 조직에 이미 있는 데이터뿐 아니라 외부 도구에서 만든 모델도 공통 표현에 연결한다.
- 분석가와 앱 개발자는 같은 객체와 속성을 활용해 분석 및 운영 앱을 만든다.
- 사용자의 판단이나 업무 액션을 온톨로지에 **write-back**하면, 운영 결과와 현장 피드백을 다시 반영할 수 있다.
- 시나리오를 비교해 의사결정을 지원하고, 필요하면 OPI(Ontology Programming Interface) 등을 통해 타사 앱에서도 온톨로지와 상호작용한다.

강의의 할인 가격 예시에서는 모델이 제안한 가격 변경과 실제 매장 데이터를 비교하고, 분석가가 이상치를 살피며, 앱이 의사결정자에게 확인할 항목을 보여준다. 의사결정자가 가격 변경을 승인하거나 조정한 결과는 온톨로지에 다시 기록된다. **데이터 → 모델 → 분석·앱 → 사람의 결정 → write-back**으로 이어지는 흐름이 온톨로지의 실질적인 쓰임이다.

### 3. 온톨로지 딥다이브 - 데이터

이 영상은 온톨로지의 첫 구성 요소인 **데이터 연결·변환·관리**를 앱 예시로 보여준다. 표 형식 데이터뿐 아니라 비정형, IoT, 지리공간 데이터와 SAP·Salesforce·Oracle 같은 상용 시스템 데이터도 연결할 수 있다.

**예시 1 — HyperAuto로 SAP 데이터 파이프라인 만들기**

- 원본 데이터를 동기화하기 전에 소스 시스템의 테이블과 메타데이터, 테이블 간 관계를 살펴본다.
- 필요한 모듈이나 사전 정의된 워크플로를 선택하면 관련 테이블을 자동으로 묶고, 수집 후 필요한 변환 파이프라인을 만든다.
- 파이프라인을 처음부터 직접 만드는 일을 줄여 사용 사례를 더 빨리 시작할 수 있다는 설명이다.

**예시 2 — Data Lineage로 데이터 흐름과 상태 추적하기**

- 분석·운영 앱에서 쓰는 데이터가 어느 소스에서 왔고, 중간에 어떤 변환을 거쳤는지 그래프로 추적한다.
- 데이터가 최신인지, 파이프라인이 정상인지, 어떤 사용자가 접근할 수 있는지 확인한다.
- 강의 예시에서는 오래된 데이터셋과 최신 데이터셋, 사용자의 접근 가능 여부를 그래프에서 구분한다.

메모: 여러 데이터 소스를 연결하는 것만으로 끝나는 게 아니다. 각 지표와 데이터셋의 출처·변환 과정·상태·권한까지 추적할 수 있어야 신뢰할 수 있는 파이프라인을 운영할 수 있다.

### 4. 온톨로지 딥다이브 - 모델

**모델은 Foundry 안에서만 만들어야 하는가? 아니다.** 외부에서 개발한 모델도 온톨로지에 연결해 사용할 수 있다. 강의에서는 AWS SageMaker, DataRobot, IBM Watson, GCP Vertex AI 등 모델 개발 도구와의 연동을 예로 든다.

**모델 라이프사이클 관리**

- 모델을 어떤 데이터셋으로 학습했는지 관리하고, 생산 데이터와 연결해 실제 운영 상황에 대응하도록 한다.
- 모델을 평가하고 이전·이후 결과를 비교하며, 출시와 배포 후에도 모니터링한다.
- 이를 위해 강의는 제출 → 평가 → 출시 → 프로덕션 배포 → 지속적 모니터링을 다루는 **Modeling Objective** 프레임워크를 소개한다.

**화면과 사례 메모**

- 데이터 과학자는 Workshop 빌딩 블록으로 이미지 주석 도구를 만들 수 있다. 의료 전문가가 학습 데이터에 주석을 달면 변경 사항이 온톨로지에 기록된다.
- **Code Workbook**에서는 데이터와 모델을 노드로 연결하고, 각 노드의 코드와 입출력 데이터의 출처를 살펴본다. R·Python·SQL과 TensorFlow·Keras·scikit-learn 같은 라이브러리를 지원한다고 소개한다.
- 학습된 모델은 온톨로지 객체의 동적 값을 갱신하고 운영 워크플로에 연결할 수 있다.
- 의료 예시에서는 의사가 프로덕션 앱에서 의료 이미지에 주석을 달거나 모델의 예측을 확인하고, 결과에 따라 방사선 전문의가 임상의에게 알리거나 추가 검사를 요청하는 흐름을 보여준다.

핵심은 모델을 만든 팀과 모델을 사용하는 현장, 모델 결과에 영향을 받는 후속 업무를 따로 두지 않고 연결하는 것이다.

### 5. 온톨로지 딥다이브 - 분석

영상에서 중심으로 소개한 분석 앱은 **Quiver**다. 코딩 전문가만을 위한 도구가 아니라, 온톨로지에 이미 구성된 객체와 데이터를 사용해 다양한 사용자가 탐색·필터링·시각화·대시보드를 만들 수 있는 노코드 분석 도구로 설명한다.

**영상에서 든 분석 예시**

- 유지보수 점검 로그를 찾아 필터링하고, 센서에서 들어오는 시계열 이벤트를 겹쳐 본다.
- 유지보수 직전에 제품 품질이 떨어지는 패턴이 보이면, 분석 결과를 근거로 점검 주기를 조정할지 검토한다.
- 데이터 과학자가 만든 모델의 예측을 같은 분석 안에서 비교한다. 실제 현장 분석이 모델 예측과 다르면 분석가가 그 피드백을 데이터 과학자에게 전달해 모델을 개선할 수 있다.
- 공급망 예시에서는 운영자가 준비된 분석 앱에서 일부 매개변수를 바꾸고, 여러 시나리오의 결과를 비교해 결정을 내린다.

**보안 메모:** 데이터 접근 권한과 온톨로지 사용 권한은 중앙에서 구성한다. 분석 도구를 사용하거나 다른 모델을 선택한다고 해서 허용되지 않은 데이터에 접근할 수 있는 것은 아니다. 사용자는 매번 접근 경계를 새로 만들기보다 권한 범위 안에서 분석과 의사결정에 집중한다.

### 6. 온톨로지 딥다이브 - 애플리케이션

분석 앱이 데이터를 살펴보는 도구라면, 이 장의 앱은 운영 담당자가 매일 수행하는 **업무 자체를 지원하는 맞춤형 앱**이다.

- **Workshop:** 온톨로지의 객체를 읽고 쓰는 로우코드 앱을 빠르게 구성한다. 이미 통합된 객체·액션·write-back 흐름을 재사용할 수 있다.
- **프로코드 앱 빌더:** 더 세밀한 맞춤화가 필요할 때 사용한다. 강의에서는 2D·3D 차트처럼 복잡한 시각화 요구를 예로 든다.
- 두 방식 모두 사용자의 액션을 캡처해 온톨로지에 write-back할 수 있어 운영에서 생긴 피드백을 다시 시스템에 반영한다.

**시나리오 앱 예시:** 사용자가 입력 화면에서 생산 관련 매개변수를 바꾸면 모델이 실행되고, 결과가 분석 화면에 바로 표시된다. 사용자가 공장 간 제품 이동량 같은 변경을 결정하면 그 액션은 온톨로지에 기록되고 SAP 같은 외부 운영 시스템에 반영될 수도 있다.

여러 앱을 사용하는 조직을 위해서는 앱과 파일을 찾기 쉽게 모아 둔 작업 공간도 필요하다. 강의에서 소개한 **Carbon**은 사용자 그룹에 맞는 앱·기능·파일을 배치해, 어떤 업무에 어디로 가야 하는지 보여주는 작업 공간 디자인 앱이다.

### 7. 온톨로지 딥다이브 - 통합

모든 사용자가 Foundry 화면에서 직접 일해야 하는 것은 아니다. 온톨로지는 API를 통해 외부 시스템과 연결할 수 있으며, 강의에서는 **OPI(Ontology Programming Interface)**를 예로 든다.

**물류 알림 예시**

- 물류센터 담당자는 주문 처리에 영향을 주는 자원·용량 부족 알림을 확인한다.
- Foundry 앱에서 알림을 처리하거나, 외부 공급업체에 추가 용량을 요청하는 이메일을 보낼 수 있다.
- 사용자의 액션은 원본 시스템에 write-back된다.
- 반대로 타사 시스템에서 처리한 액션과 최신 정보도 Foundry로 돌아올 수 있다.

즉, 사용자가 어느 화면에서 일하든 양쪽 시스템의 정보와 액션을 동기화해 공통된 정보 소스를 유지하는 것이 목표다. 기존 시스템을 모두 없애거나 Foundry를 유일한 프런트엔드로 강제하는 방식이 아니다.

## 퀴즈 결과와 복습 메모

퀴즈는 **15문항**이었다.

헷갈리기 쉬운 내용을 다시 적어 두면:

1. **Foundry는 기존 도구를 전부 대체하는 플랫폼이 아니다.** 기존 데이터 소스와 모델링 환경, 타사 앱과 연동한다.
2. **온톨로지는 데이터 저장소의 다른 이름이 아니다.** 객체·관계·작업·모델을 업무에 연결하는 운영 계층이다.
3. **사용자는 기술 직군에 한정되지 않는다.** 노코드부터 프로코드까지 역할에 맞는 도구를 사용하고, 권한에 따라 데이터를 다룬다.
4. **모델의 결과는 운영과 연결될 수 있다.** 온톨로지 엔티티를 갱신하고 그 결과를 워크플로에서 활용한다.
5. **보안은 데이터 공유와 함께 적용된다.** 적절한 권한을 설정한 채 여러 팀이 공통 온톨로지를 활용한다.
6. **운영 변경은 시나리오로 먼저 검토할 수 있다.** 실제 운영 데이터를 기반으로 특정 변경의 영향을 안전하게 시험한다.
